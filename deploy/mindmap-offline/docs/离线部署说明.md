# 离线部署说明（从零开始）

> 适用场景：部署机是 **Windows Server 2012 R2 x64**，在局域网内、无外网、无 npm registry，且与开发机网络不通。
> 本包**自带 Node.js v18.20.8 与 nginx 1.26.2 的 Windows x64 便携运行时**，目标机不需要预装 Node.js/nginx，也不需要联网。
> 架构、版本依据、数据备份、升级回滚等背景说明见 [部署文档.md](部署文档.md)。

## 0. 包内自带什么、不包含什么

自带（解压即用，不运行安装程序、不写注册表）：

- `runtimes\node\`：Node.js v18.20.8 win-x64 官方 zip 便携版（`node.exe`）。
- `runtimes\nginx\`：nginx 1.26.2 Windows 官方 zip 版（`nginx.exe` + `conf\`）。
- `web\`：myweb 前端构建产物（已改为同源 `/ws`）。
- `server\`：后端源码 + 完整 `node_modules`（含 `sql.js` 的 WASM，无需 `npm install`）。
- `nginx\nginx.template.conf`：一键部署使用的 nginx 模板（端口占位符、全部相对路径）。
- `scripts\deploy.ps1`、`start.ps1`、`stop.ps1`、`uninstall.ps1`、`check-deploy.js`。

不包含 / 需另行准备：

| 内容 | 说明 |
| --- | --- |
| Linux 运行时 | 包内只有 Windows x64 二进制，Linux 需单独准备，见第 9 节 |
| Windows 更新（KB2919355、KB2999226）与 VC++ 运行库 | 按二进制导入表**通常不需要**；仅在 `node.exe` 启动失败时补装，见 7.1 |
| 可选的 AI 服务 | 必须是部署机网络可达的 OpenAI 兼容服务，否则 AI 功能不可用 |
| 内网 HTTPS 证书 | 本包默认 HTTP；需要 HTTPS 时自行在 nginx 增加证书配置 |

## 1. 产物、体积与校验

发布产物位于仓库工作区的：

```
deploy/mindmap-offline-win2012r2-20261108.zip
deploy/SHA256SUMS.txt
deploy/产物信息.txt
```

- 解压后顶层直接是 `runtimes\`、`web\`、`server\`、`nginx\`、`scripts\`、`config\`、`logs\`、`docs\`，没有多余嵌套目录。
- 未压缩体积约 **140 MB / 4769 个文件**；压缩后体积与 SHA256 以 `deploy\产物信息.txt`、`deploy\SHA256SUMS.txt` 为准。

Windows 校验：

```powershell
Get-FileHash .\mindmap-offline-win2012r2-20261108.zip -Algorithm SHA256
```

把输出与 `SHA256SUMS.txt` 中的值比对（不区分大小写）。若不一致，说明文件在拷贝过程中损坏，请重新获取，不要继续解压部署。

解压后抽查关键文件（应全部为 `True`）：

```powershell
Test-Path .\runtimes\node\node.exe
Test-Path .\runtimes\nginx\nginx.exe
Test-Path .\web\index.html
Test-Path .\server\index.js
Test-Path .\server\node_modules\sql.js\dist\sql-wasm.wasm
```

最后一项是 sql.js 离线运行所需的 WASM 文件，缺失会导致后端启动失败。

## 2. 目标机准备

### 2.1 系统与账号

- Windows Server 2012 R2 **x64**（6.3.9600）。32 位系统不受支持。
- 建议使用有本地管理员权限的账号执行部署；部署本身不要求管理员，但防火墙放行、任务计划程序需要管理员。
- 确认磁盘空间：解压后约 140 MB，加上数据与上传文件，建议至少预留 1 GB。

### 2.2 PowerShell 版本

Server 2012 R2 默认 Windows PowerShell **4.0**。本包脚本兼容 4.0/5.1，未使用 `Expand-Archive`、`Compress-Archive` 等 PowerShell 5 专属命令。

如果执行脚本被策略拦截，用下面的方式显式绕过：

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\deploy.ps1
```

### 2.3 前置组件（UCRT / VC++）

按本包 `node.exe` / `nginx.exe` 的导入表检查，**不需要预装** Universal C Runtime 或 VC++ 运行库（详见 [部署文档.md](部署文档.md) 1.4 节）。如果 `node.exe` 无法启动，再按 7.1 节补装 KB2919355、KB2999226 与 VC++ 2015-2022 x64。

### 2.4 防火墙

默认 Web 端口 8080，需要允许局域网访问。

`deploy.ps1` 在管理员权限下会**自动创建**入站规则（名称 `MindMap Web`，TCP 当前 Web 端口，Domain/Private/Public 全部配置）；非管理员运行时只打印手动命令，不会中断部署。

如果部署脚本没有自动添加（例如用普通账号执行、或规则被组策略管理），用管理员 PowerShell 手工添加：

```powershell
New-NetFirewallRule -DisplayName "MindMap Web" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow -Profile Any
```

改过端口时把 `8080` 换成实际 `-WebPort`。重复执行会复用或更新同名规则。

不要放行 3000（后端只供本机 nginx 访问）。

## 3. Windows 一键部署

以下以部署到 `C:\mindmap` 为例。包内配置全部使用相对路径，**换成其他目录也不需要改任何文件**。

### 3.1 解压到目标目录

Server 2012 R2 默认 PowerShell 4.0 没有 `Expand-Archive`，用以下任一方式：

方式 A：资源管理器右键 zip →「全部解压缩」→ 目标路径 `C:\mindmap`。

方式 B：PowerShell + .NET（.NET 4.5 自带）：

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
[System.IO.Compression.ZipFile]::ExtractToDirectory(
  'D:\mindmap-offline-win2012r2-20261108.zip',
  'C:\mindmap'
)
```

解压后确认 `C:\mindmap\runtimes\node\node.exe` 与 `C:\mindmap\runtimes\nginx\nginx.exe` 存在。

### 3.2 执行一键部署

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\deploy.ps1
```

可选参数：

```powershell
# 改 Web 端口为 8081、后端端口为 3001
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\deploy.ps1 -WebPort 8081 -ApiPort 3001

# 强制重新生成 JWT_SECRET（会让所有已登录用户 token 失效）
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\deploy.ps1 -ForceSecret
```

脚本会自动完成：

1. 检查包内 `node.exe` / `nginx.exe` / `web` / `server` / 模板，打印 OS，执行 `node -v`、`nginx -v`。
2. 停止本包上一次启动的 server 与 nginx（重复执行不报错）。
3. 检查 Web/Api 端口是否被占用；被占用时打印占用进程并退出。
4. 生成 `config\server.env`（首次自动生成随机 `JWT_SECRET`）与 `nginx\nginx.runtime.conf`，创建 `server\data`、`server\uploads\{avatars,images}`、`logs`，并做 `nginx -t` 校验。
5. 启动后端并等待 `/api/health` 通过（最多 30 秒）。
6. 启动 nginx 并等待端口可连接；在管理员权限下自动添加 Windows 防火墙入站规则（`MindMap Web`，TCP 当前 Web 端口），非管理员时只打印手动命令。
7. 执行 `check-deploy.js` 四项自检，打印访问地址与文件位置。

预期输出（节选，实际 PID/版本以运行结果为准）：

### 3.3 客户端浏览器与验证

客户端统一为 **Windows 10 / Windows 11**，用**当前版本 Chrome 或 Edge** 访问即可；服务端不需要浏览器。

Chrome 离线安装包不包含在本压缩包内，单独存放在部署目录（与 zip 同级）：

```powershell
msiexec /i "GoogleChromeStandaloneEnterprise64.msi" /qn /norestart
```

版本、SHA256、签名见同目录的 `Chrome离线安装包说明.txt`。

1. 打开 `http://<部署机IP>:8080/`。
2. 注册一个账号（系统没有默认账号）。
3. 创建个人思维导图，编辑并刷新，确认内容保存。
4. 团队协同：用两个浏览器登录不同账号，加入同一团队并打开同一团队文件，确认两端实时同步。
5. 浏览器开发者工具 Network → WS，连接地址应为 `ws://<当前页面host>/ws/file-<id>`，状态 `101 Switching Protocols`。

### 3.4 手工复检（可选）

`check-deploy.js` 是四项自检脚本：`/api/health`、入口页、JS 资源、WebSocket 握手。`deploy.ps1` 第 7 步会自动调用它并传入实际端口；手工复检时按下面任一方式执行：

```powershell
# 方式 A：不带参数，自动读取 logs\deploy-state.json 里的 webPort（推荐）
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js

# 方式 B：显式指定完整地址（改过端口时用这个，把 8080 换成实际端口）
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js http://127.0.0.1:8080

# 方式 C：只给端口号，等价于 http://127.0.0.1:<端口>
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js 8080
```

不传参数且读不到 `logs\deploy-state.json` 时，默认检查 `http://127.0.0.1:8080`（与 `deploy.ps1` 默认 Web 端口一致）。

确认实际端口：

```powershell
Get-Content C:\mindmap\logs\deploy-state.json
netstat -ano | findstr :8080
```

`deploy-state.json` 只在 `deploy.ps1` 完整成功后写入；如果部署中途失败、文件不存在，请显式传端口。若自检地址仍是 `http://127.0.0.1` 且报 `ECONNREFUSED 127.0.0.1:80`，说明脚本是旧版本或漏了端口参数，按上面的方式 B/C 指定端口即可。

## 4. 参数、端口与重复部署

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `-WebPort` | 8080 | nginx 监听端口、页面访问端口 |
| `-ApiPort` | 3000 | 后端端口，同时写入 `config\server.env` 的 `PORT` |
| `-ForceSecret` | 关闭 | 重新生成 `JWT_SECRET` |

- 修改端口后访问地址变为 `http://<IP>:<WebPort>/`；前端 WebSocket 自动跟随页面端口，无需重新构建。
- **重复执行**：脚本先停旧实例再启动；已有 `config\server.env` 时默认保留 `JWT_SECRET` 和 AI 三项；`server\data`、`server\uploads` 不会被清空。
- **端口被占用**：脚本打印占用 PID 与进程名并退出，不会自动换端口。换端口后重新执行即可。
- **配置已存在**：直接复用，不会覆盖有效 `JWT_SECRET`；只有 `-ForceSecret` 或值为空/`CHANGE_ME` 时才生成新值。

## 5. 启动、停止、重启与卸载

不同场景对应不同脚本，不要混用：

| 场景 | 用法 | 说明 |
| --- | --- | --- |
| 首次部署 / 改端口 / 改 `server.env` | `deploy.ps1` | 会重新生成 `server.env`（保留有效 JWT）与 nginx 配置、创建防火墙规则 |
| 已部署，只是服务没在运行 | `start.ps1` | 复用现有 `server.env`，**不重新生成 JWT_SECRET**，启动后自检 |
| 已部署，需要重启 | `start.ps1` | 内部先停旧实例再启动，等价于 stop + start |
| 停止 | `stop.ps1` | 停 nginx 与后端，删除 pid 文件 |

### 5.1 启动 / 重启

```powershell
# 按 logs\deploy-state.json（缺失时读 config\server.env 与 nginx.runtime.conf）解析端口
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\start.ps1

# 显式指定端口（会在需要时用 nginx.template.conf 重新生成运行时配置）
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\start.ps1 -WebPort 8081 -ApiPort 3001
```

行为：

- 只使用已有 `config\server.env`，不会生成新的 `JWT_SECRET`；该文件缺失时直接报错并提示先执行 `deploy.ps1`。
- 端口来源优先级：命令行参数 > `logs\deploy-state.json` > `config\server.env` 的 `PORT` > `nginx\nginx.runtime.conf` > 默认 8080/3000。
- 若解析出的端口与现有 `nginx.runtime.conf` 不一致，会用 `nginx\nginx.template.conf` 重新生成配置；模板缺失时提示改用 `deploy.ps1`。
- 启动前会停掉本包上一次运行的实例，因此**重复执行 start.ps1 就是重启**。
- 启动后端与 nginx 后执行四项自检；管理员权限下同时确保 `MindMap Web` 防火墙规则存在。
- 退出码：`0` 成功；`1` 前置检查、端口占用、启动失败或自检失败。

### 5.2 停止

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\stop.ps1
```

停止 nginx（含 worker）与后端，删除 pid 文件；重复执行返回 0。pid 文件丢失时，按本包运行时路径兜底结束对应的 `nginx.exe` 与 `node.exe index.js` 进程。

### 5.3 卸载

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\uninstall.ps1
```

- 默认保留 `config\server.env`、`server\data`、`server\uploads`，只清理 pid、日志、运行时 nginx 配置与 `deploy-state.json`。
- 如需连数据一起删除：

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\uninstall.ps1 -RemoveData
```

程序文件与 `runtimes\` 不会自动删除，确认不再需要后手动删除整个 `C:\mindmap` 目录即可。没有注册表写入、没有系统服务残留。

### 5.4 开机自启

使用「任务计划程序」：

1. 打开「任务计划程序」→「创建任务」。
2. 常规：勾选「不管用户是否登录都要运行」「使用最高权限运行」。
3. 触发器：新建「启动时」。
4. 操作：程序 `powershell.exe`，参数 `-ExecutionPolicy Bypass -File C:\mindmap\scripts\start.ps1`，起始于 `C:\mindmap`。
5. 重启后浏览器验证 `http://<部署机IP>:8080/`。

## 7. 常见故障排查

### 7.1 node.exe 无法启动 / 报缺少 DLL

症状：部署脚本第 1 步输出 `bundled node.exe failed to start (exit code ...)`，或运行 `runtimes\node\node.exe -v` 报缺少 DLL。

顺序处理：

1. 确认是 **x64** 系统；不要用 32 位或 WoW64 环境。
2. 安装 **KB2919355**（Windows Server 2012 R2 2014 年 4 月更新汇总）与 **KB2999226**（Universal C Runtime），重启。
3. 仍失败时安装 **Microsoft Visual C++ 2015-2022 Redistributable (x64)**，重启后再执行 `runtimes\node\node.exe -v`。
4. 目标机不能联网时，在有外网的机器从 Microsoft Update Catalog 下载 `.msu`，VC++ 下载 `vc_redist.x64.exe`，用 U 盘摆渡。
5. 若 `node.exe -v` 能输出版本，但后端启动失败，改看 `logs\server.err.log`。

> 说明：本包二进制的静态导入表不含 UCRT/VC++ 依赖，上述步骤是“目标机缺系统更新”时的兜底，不是常规必需。

### 7.2 端口被占用

症状：脚本第 3 步输出 `port 8080 is already in use by PID ...`，或后端/nginx 启动失败。

```powershell
netstat -ano | findstr :8080
netstat -ano | findstr :3000
```

根据 PID 在任务管理器确认进程；不要随意结束未知系统进程。处理方式：

- 换端口重新部署：`deploy.ps1 -WebPort 8081 -ApiPort 3001`。
- 或停止占用端口的程序后再执行。

### 7.3 nginx 配置测试失败

脚本第 4 步会执行 `nginx -c ..\..\nginx\nginx.runtime.conf -t`，失败时输出具体原因：

- `CreateFile() ... failed (2: The system cannot find the file specified)`：通常是手工把配置改成了绝对路径，或把 `nginx.runtime.conf` 放错位置。请恢复为 `deploy.ps1` 生成的相对路径配置，不要用 `-p` 参数。
- `open() ... mime.types failed`：模板中的 `include` 必须保持 `../runtimes/nginx/conf/mime.types`（相对配置文件目录），不要改成 `conf/mime.types`。
- `unknown variable "connection_upgrade"`：`map` 段落被漏掉或不在 `http{}` 层级。

### 7.4 页面 404 / 空白

1. 确认 `C:\mindmap\web\index.html` 存在。
2. 确认访问的是 `http://<IP>:8080/`，不是后端 `:3000`（后端不提供前端页面）。
3. nginx 的 `root` 是 `../../web`（相对 `runtimes\nginx`），不要改成 `web/dist`。
4. 直接请求静态资源，确认返回 200：

```powershell
$js = Get-ChildItem C:\mindmap\web\assets -Filter 'index-*.js' | Select-Object -First 1
$r = Invoke-WebRequest -UseBasicParsing ('http://127.0.0.1:8080/assets/' + $js.Name)
$r.StatusCode
$r.Headers['Content-Type']
```

404 多为解压不完整；403 检查 nginx 进程对 `web\` 的读取权限。

### 7.5 WebSocket 连不上 / 协同不生效

1. 确认用 nginx 地址访问（默认 8080），而不是直接访问 3000。
2. 确认 `nginx\nginx.runtime.conf` 含 `/ws` 段落与三行升级头：

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection $connection_upgrade;
```

3. 运行自检第 4 项（不带参数时会读 `logs\deploy-state.json` 的实际端口，读不到默认 8080）：

```powershell
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js
```

若改过端口或部署状态文件缺失，显式传入：`... check-deploy.js http://127.0.0.1:<WebPort>` 或 `... check-deploy.js <WebPort>`。

4. 后端没启动时 `/api/health` 与 WS 都会失败；先看 `logs\server.err.log`。
5. 如果使用旧 `dist`（未采用本包 `web/`），前端可能仍写死 `ws://hostname:3000/ws`，按 [部署文档.md](部署文档.md) 2.2 节改为同源并重新构建。

### 7.6 数据库文件权限 / 启动失败

症状：`logs\server.err.log` 出现 `EACCES`、`EPERM`、文件写入错误，或 `Failed to start server`。

- 确认运行后端与创建 `server\data` 的账号一致，不要先用管理员生成 `app.db` 再用普通账号启动。
- 检查 `server\data` 的 NTFS 权限，确保运行账号有“修改/写入”。
- 杀毒软件/同步工具可能锁定 `app.db`，把部署目录加入白名单。
- `app.db` 损坏时不要直接删除；先备份损坏文件，再尝试恢复最近备份。

### 7.7 上传失败 / 历史图片 404

- `server\index.js` 启动时会自动创建 `server\uploads`、`avatars`、`images`；目录被删后重启会重建空目录，但**历史文件不会自动恢复**。
- 检查 `/static/` 是否被 nginx 转发：直接访问 `http://127.0.0.1:8080/static/avatars/<文件名>` 应返回图片。
- 历史文件只能从备份恢复 `server\uploads\`。
- 上传 10MB 限制由 multer 控制；请求体总限制 20MB。

### 7.8 502 / 504 Bad Gateway

- 502：nginx 连不上后端。确认后端进程存在、`config\server.env` 的 `PORT` 与 `nginx\nginx.runtime.conf` 的 `proxy_pass` 一致。
- 504：请求超时。普通 API 为 300s；AI 流式接口单独配置 3600s 且关闭缓冲。
- 改配置后重新执行 `deploy.ps1`（会重写配置并重启）。

### 7.9 401 / 登录后立即失效

- 修改/重新生成 `JWT_SECRET` 会导致旧 token 全部失效，用户重新登录即可。
- 多实例部署时各实例 `JWT_SECRET` 必须一致。
- 检查客户端是否带 `Authorization: Bearer <token>`。

### 7.10 请求体过大（413）

后端 Express JSON 限制 20MB，图片上传限制 10MB，nginx `client_max_body_size 20m`。如需更大，三处都要调整：`server/index.js` 的 `express.json/urlencoded`、`server/routes/upload.js` 的 `limits`、`nginx/nginx.template.conf` 的 `client_max_body_size`。

### 7.11 AI 功能报“未配置”或 502

- “未配置”：用户个人中心未填写，且系统 `AI_BASE_URL/AI_API_KEY/AI_MODEL` 未配齐。
- 502/连接失败：从部署机测试 AI 地址可达性；内网完全隔离且没有 AI 网关时，AI 不可用是预期行为。
- AI Key 保存在 `user_configs` 表中；恢复数据库备份会同时恢复这些配置。

### 7.12 局域网无法访问

1. 先在部署机本机访问 `http://127.0.0.1:8080/`，确认服务本身正常。
2. 确认 nginx 监听的是所有网卡，而不是 `127.0.0.1`：

```powershell
Select-String 'listen' C:\mindmap\nginx\nginx.runtime.conf
netstat -ano | findstr :8080
```

`listen` 应为 `0.0.0.0:8080`；`netstat` 的本地地址应为 `0.0.0.0:8080` 或 `[::]:8080`。若显示 `127.0.0.1:8080`，说明配置被手工改过，恢复 `nginx\nginx.template.conf` 后重新执行 `deploy.ps1`（会自动重新生成运行时配置）。

3. 确认防火墙放行规则存在（管理员 PowerShell）：

```powershell
Get-NetFirewallRule -DisplayName 'MindMap Web' | Select-Object DisplayName,Enabled,Action,Profile
```

没有规则或 `Enabled` 为 `False` 时，重跑 `deploy.ps1`（管理员权限会自动创建），或手工执行：

```powershell
New-NetFirewallRule -DisplayName "MindMap Web" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow -Profile Any
```

4. 从另一台客户端测试端口连通性：

```powershell
Test-NetConnection <部署机IP> -Port 8080
```

`TcpTestSucceeded` 为 `True` 说明网络与防火墙已通，问题应在前端/浏览器；为 `False` 时继续检查防火墙、交换机 ACL、云主机安全组或多网卡绑定。

5. 确认访问的是 `http://` 而不是 `https://`：对 HTTP 端口用 HTTPS 会直接失败。

## 8. 升级与回滚（保留数据与上传目录）

1. 停止服务：`scripts\stop.ps1`。
2. 备份（PowerShell 4.0 可用，不要用 `Compress-Archive`）：

```powershell
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$dst = "C:\mindmap-backup\$stamp"
New-Item -ItemType Directory -Force -Path $dst | Out-Null
Copy-Item .\server\data -Destination $dst -Recurse -Force
Copy-Item .\server\uploads -Destination $dst -Recurse -Force
Copy-Item .\config\server.env -Destination $dst -Force
```

3. 新包解压到新目录，把上面的 `server.env`、`data`、`uploads` 复制到新目录对应位置。
4. 旧目录改名备份，新目录改为 `C:\mindmap`，执行 `scripts\deploy.ps1`。
5. 自检全部通过、浏览器抽样验证后再删除旧目录。

### 8.1 已部署机器上的热更新（不覆盖数据）

如果只是修复局域网访问（nginx `listen` 改为 `0.0.0.0`、`deploy.ps1` 自动加防火墙规则）、自检默认端口或 `server.env` 双行格式问题，不需要重新解压整个包，也不会改动 `server\data`、`server\uploads`。

先判断目标机上的脚本是新版还是旧版（二选一）：

```powershell
# 方法 1：查版本标记（2026-11-08-r2 及以后的新版才有）
Select-String -Path C:\mindmap\scripts\deploy.ps1,C:\mindmap\scripts\start.ps1 -SimpleMatch '2026-11-08-r2'

# 方法 2：查旧格式自修复逻辑的关键字（有输出=新版）
Select-String -Path C:\mindmap\scripts\start.ps1 -SimpleMatch 'server.env legacy format repaired'
```

两个脚本都带版本标记时才是本轮新版。旧版 `deploy.ps1` 会把 `KEY=` 的值写到下一行，旧版 `start.ps1` 只会读配置、不会修复。

从新 zip 中只覆盖这些文件（保留原目录结构，不会碰 `web/`、`server/data`、`server/uploads`、`config/server.env`）：

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip = 'D:\mindmap-offline-win2012r2-20261108.zip'
$dst = 'C:\mindmap'
$z = [System.IO.Compression.ZipFile]::OpenRead($zip)
foreach ($n in @('scripts/deploy.ps1','scripts/start.ps1','scripts/stop.ps1','scripts/uninstall.ps1','scripts/check-deploy.js','nginx/nginx.template.conf')) {
  $target = Join-Path $dst ($n -replace '/', '\')
  [System.IO.Compression.ZipFileExtensions]::ExtractToFile($z.GetEntry($n), $target, $true)
}
$z.Dispose()
```

然后用**管理员** PowerShell 重新执行 `scripts\deploy.ps1`（按新模板重新生成 `nginx\nginx.runtime.conf`、创建防火墙规则、自检）或 `scripts\start.ps1`（快速重启并创建防火墙规则；端口未变时复用现有 nginx 配置）。两者都不会改动 `data`、`uploads`；`JWT_SECRET` 仅在为空或 `CHANGE_ME` 时重新生成。

> 若原部署用的是非默认端口，执行 `deploy.ps1` 时请传入相同的 `-WebPort` / `-ApiPort`（端口可从 `logs\deploy-state.json` 或 `nginx\nginx.runtime.conf` 查看），否则会按默认 8080/3000 重写配置。

> **重要（配置修复）**：旧版 `deploy.ps1` 写 `config\server.env` 时会把值写到下一行，实际读到的是空 `JWT_SECRET`。新版两个脚本都会在读取配置时识别这种「`KEY=` 一行、值一行」的旧格式，自动合并为单行并回写，**保留原密钥与 AI 配置不变**，并在控制台打印 `server.env legacy format repaired`。因此替换脚本后直接执行 `start.ps1` 即可完成修复与重启，不必再跑 `deploy.ps1`；只有两行都为空或值为 `CHANGE_ME` 时，`deploy.ps1` 才会生成新密钥（旧 token 本来就不可用，重新登录即可）。

执行后确认写出的是单行键值：

```powershell
Get-Content C:\mindmap\config\server.env | Select-String 'JWT_SECRET','PORT'
# 期望：JWT_SECRET=<96 位十六进制> 与 PORT=<端口> 各占一行，等号后紧跟值
```

若仍是 `JWT_SECRET=` 一行、值在下一行，说明替换上去的还是旧脚本，请回到上面的哈希/关键字检查。

如果暂时不想重跑脚本，只想让局域网马上能访问，手工添加防火墙规则即可（见 2.4），无需其它改动。

回滚：停服务 → 新目录移开 → 旧目录改回 `C:\mindmap` → 如已产生新数据，用升级前备份恢复 `app.db` 与 `uploads` → 执行旧目录的启动脚本。

## 9. Linux 的限制与运行时准备

本包**只有 Windows x64 运行时**，Linux 上不能直接使用 `runtimes\node` / `runtimes\nginx`，也没有 Linux 一键脚本。不要假设“解压即用”。

限制：

- Windows 一键脚本 `deploy.ps1` / `stop.ps1` / `uninstall.ps1` 依赖 PowerShell，Linux 不可用。
- Linux 需自行准备 node 与 nginx，并手工启动后端（包内不提供 Linux 启动脚本）。
- 目标机无外网时，运行时必须从联网机器摆渡。

在联网机器准备（步骤）：

1. **Node.js**：下载 `https://nodejs.org/dist/v18.20.8/node-v18.20.8-linux-x64.tar.xz`，用同目录 `SHASUMS256.txt` 校验 SHA256。
2. 摆渡到目标机后解压，例如：

```bash
sudo tar -xJf node-v18.20.8-linux-x64.tar.xz -C /opt
sudo ln -s /opt/node-v18.20.8-linux-x64/bin/node /usr/local/bin/node
sudo ln -s /opt/node-v18.20.8-linux-x64/bin/npm  /usr/local/bin/npm
/usr/local/bin/node -v    # 应输出 v18.20.8
```

3. **nginx**：优先使用发行版 ISO/本地仓库的 RPM/DEB 离线包；或从 `https://nginx.org/download/nginx-1.26.2.tar.gz` 下载源码，在联网机器准备好 gcc/pcre/zlib/openssl 后编译，再把 `objs/nginx` 与 `conf/` 摆渡过去。
4. **部署**：

```bash
sudo mkdir -p /opt/mindmap
sudo unzip mindmap-offline-win2012r2-20261108.zip -d /opt/mindmap
sudo useradd -r -s /sbin/nologin mindmap || true
sudo chown -R mindmap:mindmap /opt/mindmap
# 编辑 config/server.env（JWT_SECRET；PORT 保持 3000）
# 用 nginx/nginx.linux.conf 配置 nginx，nginx -t 通过后启动
cd /opt/mindmap/server
set -a; . ../config/server.env; set +a
/usr/local/bin/node index.js > ../logs/server.log 2>&1 &
/usr/local/bin/node /opt/mindmap/scripts/check-deploy.js http://127.0.0.1
```

5. 长期运行请使用发行版自带的服务管理（如自行编写 systemd 单元）；包内不再附带 Linux 启动脚本或单元文件。

> Linux 上没有类似 `deploy.ps1` 的“一键全部完成”脚本，需要按上述步骤手工准备运行时与 nginx。这是本包当前的能力边界。

## 10. 在开发机重新构建前端（可选）

部署机不需要构建。只有在修改前端源码后，才需要在开发机执行：

```bash
cd myweb
npm run build
```

要求 `myweb/node_modules` 已存在，且仓库中存在与 `myweb` 同级的 `simple-mind-map` 目录（`myweb/vite.config.js` 将 `simple-mind-map` 别名指向 `../simple-mind-map`）。构建产物在 `myweb/dist/`，把它复制到部署包的 `web/` 覆盖即可。
