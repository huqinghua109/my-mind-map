# 思维导图系统部署文档

> 目标系统：**Windows Server 2012 R2 x64**（OS 版本 6.3.9600）。
> 部署形态：包内自带 Windows x64 运行时（Node.js + nginx），解压后执行 `scripts\deploy.ps1` 即可完成配置生成、服务启动和自检；目标机不需要预装 Node.js 或 nginx，也不需要联网。
> 本文中的版本、端口、路径均以本部署包实际内容和仓库源码为依据；无法从官方文档直接证实的部分会明确标注。

## 1. 目标系统与运行时版本（锁定依据）

### 1.1 版本汇总

| 组件 | 选定版本 | 包内位置 | 校验值（SHA256） |
| --- | --- | --- | --- |
| 操作系统 | Windows Server 2012 R2 x64（6.3.9600） | — | — |
| Node.js | **v18.20.8 win-x64** 官方 zip 便携版 | `runtimes\node\node.exe` | `1a1e40260a6facba83636e4cd0ba01eb5bd1386896824b36645afba44857384a` |
| nginx | **1.26.2** Windows 官方 zip 版 | `runtimes\nginx\nginx.exe` | `942638cc31c836fe429fde22e4c46e497f89d3c2bbce46cd2c8800854fd71409`（由官方 zip 计算） |
| PowerShell | Windows PowerShell 4.0 及以上 | 系统自带 | — |

两个运行时都是**便携版**：不运行安装程序、不写注册表、不注册服务。删除部署目录即可移除运行时本体。

### 1.2 Node.js 为什么锁定 18.20.8

依据（均来自 Node.js 官方资料，不是凭印象）：

1. Node.js v18 `BUILDING.md` 的 Support list 写明：
   - `Windows x64, x86 (WoW64) | >= Windows 10/Server 2016 | Tier 1`
   - `Windows x64, x86 | Windows 8.1/Server 2012 | Experimental`
   - 同一文档还有总则：**“Node.js does not support a platform version if a vendor has expired support for it. This is true regardless of entries in the table below.”**
   来源：<https://github.com/nodejs/node/blob/v18.x/BUILDING.md#supported-platforms>
2. Node.js 18 发布公告写明：对于厂商已结束支持的系统，Node.js 18 的支持会提前结束，其中举例 **Windows 8.1（2023 年 1 月）与 Windows Server 2012 R2（2023 年 10 月）**。
   来源：<https://nodejs.org/en/blog/announcements/v18-release-announce>
3. Node.js 20/22 的 `BUILDING.md` 只把 `>= Windows 10 / Server 2016` 列为 Tier 1；Windows 8.1/Server 2012 仅剩 Experimental 行，且同样受“厂商已结束支持即不受支持”的总则约束。Server 2012 R2 的微软扩展支持已于 2023-10-10 结束，因此 **Node.js 20 起不再提供对 Server 2012 R2 的官方支持**。
   来源：<https://github.com/nodejs/node/blob/v20.x/BUILDING.md#supported-platforms>
4. `nodejs.org/dist/index.json` 中 v18 系列最后一个版本是 **v18.20.8**（2025-03-27 发布）；Node.js 18 已于 **2025-04-30** 结束生命周期（EOL）。
   来源：<https://nodejs.org/dist/index.json>、<https://nodejs.org/en/about/previous-releases>

结论与取舍：

- 选择 **18.20.8** 而不是更早的 18.x，是因为它是 v18 系列最后一个版本，包含该系列全部后续修复；该版本在本项目实测可以正常启动后端、创建 sql.js 数据库、完成 WebSocket 协同握手。
- **必须明确的风险**：严格按官方口径，Server 2012 R2 属于厂商已 EOL 的系统，Node.js 18 对它的“官方支持”在 2023-10 就已结束；18.20.8 属于“可运行、但不在官方支持窗口内”的务实选择。Node.js 18 本身也已 EOL（2025-04-30），不再接收安全修复。若条件允许，应优先升级到 Windows Server 2016 及以上并使用 Node.js 20/22 LTS。
- 本项目依赖均为纯 JS（`sql.js` 使用 WASM、`ws`/`y-websocket` 为纯 JS），没有需要本地编译的原生模块，因此 Node 18 不存在 ABI/编译兼容问题；已实测 `sql.js` WASM 加载、Express 服务、WebSocket 握手均正常。

### 1.3 nginx 为什么选 1.26.2 Windows 版

依据：

1. nginx 官方 Windows 文档说明：Windows 版使用原生 Win32 API，只使用 `select()`/`poll()` 连接处理方式，官方将其定位为 **beta** 版本；文档只给出下载与运行方法，**没有公布最低 Windows 版本要求**。
   来源：<https://nginx.org/en/docs/windows.html>
2. 官方下载页提供 `nginx/Windows-1.26.2` 的 zip 与 PGP 签名：
   来源：<https://nginx.org/en/download.html>、<https://nginx.org/download/nginx-1.26.2.zip>
3. 对本包内 `nginx.exe` 做 PE 导入表检查：只依赖 `advapi32.dll`、`crypt32.dll`、`kernel32.dll`、`user32.dll`、`ws2_32.dll`，**没有** `api-ms-win-crt-*`、`ucrtbase.dll`、`vcruntime140.dll` 等 UCRT/VC++ 依赖，也没有 delay-load 依赖。因此 2012 R2 不会因为缺少运行库而导致 nginx 无法启动。

结论与限制：

- 官方没有声明 Server 2012 R2 为受测平台，本包选择 1.26.2 是“官方 zip + 依赖面兼容”的组合，**需要在目标机上实测确认**；本开发机（Windows 11）已实测通过。
- nginx Windows 版是 beta，只有单个 worker 实际工作，适合本项目的内网小规模部署，不适合高并发场景。
- 官方 1.26 分支当前还有 1.26.3；如需更新，可在联网机器下载 `nginx-1.26.3.zip` 覆盖 `runtimes\nginx\`（本包的配置写法不变），覆盖后重新执行 `scripts\deploy.ps1` 即可。本包锁定 1.26.2 是因为它已完成端到端验证。

### 1.4 系统前置组件：UCRT / VC++ 运行库是否需要预装

结论：**按二进制依赖检查，不需要预装 Universal C Runtime 或 VC++ 运行库。**

检查方法与结果（2026-11-08 在本开发机执行）：

- 用 `pefile` 读取两个可执行文件的导入表与 delay-load 导入表：
  - `node.exe` 导入：`advapi32`、`bcrypt`、`crypt32`、`dbghelp`、`iphlpapi`、`kernel32`、`psapi`、`user32`、`userenv`、`winmm`、`ws2_32`；delay-load 为空。
  - `nginx.exe` 导入：`advapi32`、`crypt32`、`kernel32`、`user32`、`ws2_32`；delay-load 为空。
  - 两者都没有 `api-ms-win-crt-*`、`ucrtbase.dll`、`vcruntime140*.dll`、`msvcp140.dll`。
- `node.exe` 的 `kernel32` 导入函数均为 Windows 7/8 时代已有的 API（未出现 `SetThreadDescription` 等 Windows 10 才有的静态导入），因此 Server 2012 R2 的内核 API 面足够。

仍建议在目标机准备（不是“必须”，而是“出问题时按顺序补”）：

1. **KB2919355**：Windows Server 2012 R2 的 2014 年 4 月更新汇总，很多后续更新以它为前置。
2. **KB2999226**：Universal C Runtime（UCRT）。虽然本包二进制不直接依赖它，但若目标机后续自行安装其他工具/模块，通常会需要。
3. **Microsoft Visual C++ 2015-2022 Redistributable (x64)**：仅在 `node.exe` 或 `nginx.exe` 启动报缺少 DLL 时才需要；本包二进制本身不需要。
4. 目标机应是 **x64**，不要使用 32 位系统或 WoW64 环境。

获取方式（目标机不能联网时）：

- 在有外网的机器从 Microsoft Update Catalog 下载上述 KB 的 `.msu`，以及 VC++ Redistributable 的 `vc_redist.x64.exe`，用 U 盘/内网摆渡复制到目标机。
- 安装 KB 后通常需要重启；重启完成再执行部署脚本。

`scripts\deploy.ps1` 的前置检查会：

- 打印当前 OS 名称与版本；版本不是 `6.3.*` 时给出黄色警告（仍继续，便于在开发机验证）。
- 先执行 `runtimes\node\node.exe -v` 与 `runtimes\nginx\nginx.exe -v`；任一无法启动就直接失败，并在错误信息中给出上面的 KB/VC++ 处理建议。

### 1.5 PowerShell 兼容性（Server 2012 R2 默认 4.0）

Server 2012 R2 默认自带 Windows PowerShell 4.0（可自行升级到 5.1）。本包脚本只使用 PowerShell 3.0 起就存在的语法与命令，未使用仅 PowerShell 5 才提供的命令：

- 使用：`Get-CimInstance`、`Get-NetTCPConnection`、`Get-NetIPAddress`、`Start-Process -WorkingDirectory`、`ConvertTo-Json`、`Get-Content -Raw/-Tail`、`[ordered]@{}`、`$PSScriptRoot`。
- 未使用：`Expand-Archive`、`Compress-Archive`（这两个是 PowerShell 5 新增；文档中的解压/备份步骤已改成 4.0 可用的方式）。
- `Get-NetTCPConnection` 属于 Windows 8/2012 起自带的 NetTCPIP 模块；脚本还内置了 `netstat` 与 .NET `TcpClient` 兜底，避免个别环境漏检。

运行脚本时建议显式绕过执行策略（Server 2012 R2 默认可能是 Restricted）：

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\deploy.ps1
```

## 2. 整体架构与组件角色

```
浏览器
  │  http://<部署机IP>:8080/
  ▼
包内 nginx（runtimes\nginx\nginx.exe）:8080
  ├─ /             → web/ 静态文件（SPA，找不到文件回退 index.html）
  ├─ /assets/*     → web/assets/ 静态资源（长缓存）
  ├─ /api/*        → 反向代理 http://127.0.0.1:3000
  ├─ /static/*     → 反向代理 http://127.0.0.1:3000（头像、节点图片）
  └─ /ws           → 反向代理 http://127.0.0.1:3000（WebSocket，需 Upgrade）
                              │
                              ▼
                    包内 Node.js（runtimes\node\node.exe）:3000
                    ├─ Express：/api/auth、/api/user、/api/teams、/api/files、/api/upload、/api/ai
                    ├─ WebSocket：y-websocket 协同，路径 /ws/<room>
                    ├─ sql.js：数据库快照 server/data/app.db
                    └─ 上传目录 server/uploads/{avatars,images}
```

| 组件 | 角色 | 依据 |
| --- | --- | --- |
| 包内 nginx | 静态站点、API/上传文件/WebSocket 反向代理、入口缓存控制 | `nginx/nginx.template.conf`（部署时生成 `nginx/nginx.runtime.conf`） |
| 包内 Node.js | 认证、用户、团队、文件、上传、AI 代理、协同 WebSocket | `server/index.js`、`server/routes/*`、`server/ws.js` |
| sql.js | 纯 JS SQLite 实现，数据持久化为单个 `app.db` 文件 | `server/db.js` |
| y-websocket | 基于 Yjs 的实时协同，前端连接 `/ws/file-<id>` | `server/ws.js`、`myweb/src/pages/Edit.vue` |
| myweb 前端 | 构建产物 `web/`，请求 `/api`、`/static`、`/ws` | `myweb/vite.config.js`、`myweb/src/api/request.js` |

### 2.1 与仓库根目录 Dockerfile / nginx.conf 的关系

仓库根目录的 [Dockerfile](file:///c:/Users/dean12600k/Desktop/my-mind-map/Dockerfile) 和 [nginx.conf](file:///c:/Users/dean12600k/Desktop/my-mind-map/nginx.conf) 是上游 simple-mind-map Web 的静态示例：只监听 80、只服务静态文件，**没有 `/api`、`/static`、`/ws` 转发**，不能直接用于本项目。本部署包在 `nginx/` 下提供了补充了反向代理的模板。

仓库根目录 `copy.js` 会把 `dist/index.html` 复制到根目录，这是上游 Dockerfile 的打包方式；本项目部署直接使用 `myweb/dist` 作为 nginx 静态根目录，不依赖该脚本。

### 2.2 WebSocket 地址说明（重要）

旧版前端把协同地址写死为 `ws://<当前hostname>:3000/ws`，在 nginx 反代到 8080 端口后浏览器会连接 `部署机:3000`，导致协同连不上。

本部署包已修改 [Edit.vue](file:///c:/Users/dean12600k/Desktop/my-mind-map/myweb/src/pages/Edit.vue#L1038-L1042) 并重新构建，规则为：

```js
const wsUrl = (window.location.protocol === 'https:' ? 'wss://' : 'ws://') + window.location.host + '/ws'
```

即**同源**连接：页面是 `http://192.168.1.10:8080/`，WebSocket 就是 `ws://192.168.1.10:8080/ws`；改端口也不用重新构建前端。前提是 nginx 必须正确转发 `/ws`。

如果你不使用本包内 `web/`，而是用旧 `dist` 或其他分支构建，则必须按以下任一方式处理：

1. **推荐**：把前端代码改为同源 `window.location.host + '/ws'`，在开发机执行 `cd myweb && npm run build`，把新的 `dist` 覆盖 `web/`。
2. 或让 nginx 同时监听 3000 端口并转发 `/ws`，使浏览器能访问部署机 3000；但这会把后端端口暴露到局域网，不推荐。

## 4. 端口与访问地址

| 端口 | 用途 | 默认值 | 暴露范围 |
| --- | --- | --- | --- |
| Web | nginx：页面、API、静态文件、WebSocket | **8080**（`-WebPort` 可改） | 局域网用户访问 |
| API | Node 后端 | **3000**（`-ApiPort` 可改，同时写入 `config\server.env` 的 `PORT`） | 只允许本机 nginx 访问，建议防火墙禁止局域网直连 |

访问地址（`deploy.ps1` 自检后会打印）：

- 页面：`http://<部署机IP>:8080/`
- 健康检查：`http://<部署机IP>:8080/api/health`
- 协同 WebSocket：`ws://<部署机IP>:8080/ws`（前端自动按页面同源拼接）

> 后端 `server.listen(PORT)` 监听所有网卡，代码没有单独的 `HOST` 配置。若希望 3000 只被本机访问，请在 Windows 防火墙层限制 3000 的入站来源。
>
> nginx 模板使用 `listen 0.0.0.0:<WebPort>`，显式绑定所有网卡，局域网客户端可直接访问；`deploy.ps1` 在管理员权限下会自动创建对应的入站放行规则（`MindMap Web`）。

> 改端口只需重新执行 `deploy.ps1 -WebPort <端口> -ApiPort <端口>`；脚本会重写 `config\server.env` 与 `nginx\nginx.runtime.conf`，并重启两个进程。前端无需重新构建。

## 5. 环境变量

后端没有引入 dotenv，环境变量由 `deploy.ps1` / `start.ps1` 读取 `config\server.env` 后注入到子进程。

| 变量 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `JWT_SECRET` | 是 | 首次部署自动生成 48 字节随机 hex | JWT 签名密钥，生产必须唯一。`deploy.ps1` 检测到空值或 `CHANGE_ME` 会自动生成；已有有效值则保留，除非加 `-ForceSecret`。修改后所有已签发 token 失效，用户需重新登录。 |
| `PORT` | 否 | `3000` | 后端 HTTP 端口，由 `-ApiPort` 写入。 |
| `AI_BASE_URL` | 否 | 空 | 系统级 AI 兜底 Base URL，例如 `http://ai.internal/v1`。 |
| `AI_API_KEY` | 否 | 空 | 系统级 AI 兜底 API Key。 |
| `AI_MODEL` | 否 | 空 | 系统级 AI 兜底模型名。 |

补充说明：

- `config\server.env` 必须保持 **ASCII-only**（`deploy.ps1` 生成的也是 ASCII 注释）。Windows PowerShell 5 读取无 BOM 的 UTF-8 文件时会按 ANSI 解析，中文注释可能导致后面的 `JWT_SECRET` 被吞掉。
- AI 配置优先使用用户在「个人中心 - AI 配置」保存的值，用户未配置时才使用系统兜底；三项缺任意一项时 AI 功能提示未配置。
- AI 服务必须从**部署机**网络可达。完全隔离的内网若没有可访问的 AI 网关，AI 功能不可用，但不影响其他功能。
- 修改 `config\server.env` 后执行一次 `scripts\deploy.ps1`（会保留 JWT_SECRET 并重启）即可生效。

## 6. 数据文件、上传目录与备份

### 6.1 数据文件

| 路径 | 内容 | 生成方式 |
| --- | --- | --- |
| `server/data/app.db` | 用户、团队、成员、邀请、文件内容、用户 AI 配置 | 首次启动 `db.js` 自动建表并写入空库 |
| `server/uploads/avatars/` | 头像文件，URL 为 `/static/avatars/<文件名>` | 用户上传头像时 |
| `server/uploads/images/` | 思维导图节点图片，URL 为 `/static/images/<文件名>` | 编辑器上传节点图片时 |

`app.db` 由 sql.js 在内存中操作，普通数据库变更约 300ms 防抖写回整个文件；协同编辑内容还会先经过 WebSocket 层，在停止编辑约 3 秒后写入数据库（见 `server/ws.js` 的 `schedulePersist`）。**备份时请先停止后端**，避免复制到写入过程中的文件，也确保最后的协同内容已落盘。

### 6.2 备份（PowerShell 4.0 可用）

Server 2012 R2 默认 PowerShell 4.0 没有 `Compress-Archive`，下面用目录复制方式备份（也可自行用 7-Zip 压缩）：

```powershell
# 在部署根目录 C:\mindmap 下执行
powershell -ExecutionPolicy Bypass -File .\scripts\stop.ps1

$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$dst = "C:\mindmap-backup\$stamp"
New-Item -ItemType Directory -Force -Path $dst | Out-Null
Copy-Item -Path .\server\data    -Destination $dst -Recurse -Force
Copy-Item -Path .\server\uploads -Destination $dst -Recurse -Force
Copy-Item -Path .\config\server.env -Destination $dst -Force

# 备份完成后再启动
powershell -ExecutionPolicy Bypass -File .\scripts\deploy.ps1
```

备份内容应至少包含 `server\data\app.db`、`server\uploads\`、`config\server.env`。`server.env` 含 JWT 密钥与可能的系统 AI Key，备份文件需按敏感数据管理。

### 6.3 恢复

1. 执行 `scripts\stop.ps1` 停止服务。
2. 把备份中的 `server\data\app.db`、`server\uploads\` 放回对应目录，保持目录权限。
3. 如需要，恢复 `config\server.env`。
4. 执行 `scripts\deploy.ps1`，确认自检全部通过。

> 恢复旧 `app.db` 会同时回滚用户、团队和文件内容，上传目录应与同一时间点的备份一起恢复，避免图片引用丢失。

### 6.4 文件权限

后端进程需要对以下目录有读写权限：

- `server\data\`（创建和覆盖 `app.db`）
- `server\uploads\avatars\`、`server\uploads\images\`
- `logs\`（写 pid、日志、deploy-state.json）
- `nginx\`（写 `nginx.runtime.conf`）

不要先用管理员账号启动生成文件、再用普通账号启动；运行账号要保持一致。杀毒软件/文件同步工具可能锁定 `app.db`，必要时把部署目录加入白名单。

## 7. 日志

| 日志 | 位置 | 产生方式 |
| --- | --- | --- |
| 后端标准输出 | `logs\server.out.log` | `deploy.ps1` 的 `Start-Process -RedirectStandardOutput` |
| 后端错误输出 | `logs\server.err.log` | `deploy.ps1` 的 `-RedirectStandardError` |
| 后端 PID | `logs\server.pid` | `deploy.ps1` 写入 |
| nginx 访问日志 | `logs\nginx-access.log` | `nginx\nginx.template.conf` 的 `access_log` |
| nginx 错误日志 | `logs\nginx-error.log` | 同一模板的 `error_log` |
| nginx 标准输出/错误 | `logs\nginx.out.log`、`logs\nginx.err.log` | `deploy.ps1` 启动 nginx 时的重定向；通常为空 |
| nginx PID | `logs\nginx.pid` | 同一模板的 `pid` |
| 部署状态 | `logs\deploy-state.json` | `deploy.ps1` 写入（端口、版本、部署时间） |

应用没有内置滚动切割，长期运行需自行轮转。Windows 简单做法：停止服务 → 把 `logs\server.out.log` 重命名为 `server-YYYYMMDD.log` → 重新执行 `start.ps1`。

常用查看命令（PowerShell 4.0 可用）：

```powershell
Get-Content .\logs\server.err.log -Tail 50
Get-Content .\logs\nginx-error.log -Tail 50
Get-Content .\logs\deploy-state.json
```

## 8. 一键脚本用法（Windows）

### 8.1 部署：`scripts\deploy.ps1`

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\deploy.ps1
```

参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `-WebPort` | `8080` | nginx 监听端口，写入 `nginx.runtime.conf` |
| `-ApiPort` | `3000` | 后端端口，写入 `config\server.env` 的 `PORT` 与 nginx 反代目标 |
| `-ForceSecret` | 关闭 | 强制重新生成 `JWT_SECRET`（会使所有已登录 token 失效） |

脚本固定执行 7 个步骤：

1. **前置检查**：确认 `runtimes\node\node.exe`、`runtimes\nginx\nginx.exe`、`web\`、`server\`、`nginx\nginx.template.conf` 存在；打印 OS；执行 `node -v`、`nginx -v`，失败时给出 KB/VC++ 处理建议。
2. **停止旧实例**：读取 `logs\*.pid` 并 `taskkill /PID /T /F`；同时清理从本包 `runtimes\nginx` 启动的残留 nginx 进程。重复执行不会报错。
3. **端口检查**：用 `Get-NetTCPConnection` + `netstat` + .NET `TcpClient` 三重判断；端口被占用时给出占用 PID/进程名并退出（退出码 1），不会静默改端口。
4. **生成配置与目录**：创建 `config\`、`logs\`、`server\data\`、`server\uploads\{avatars,images}\`；读取旧 `server.env`，保留有效 `JWT_SECRET` 与 AI 三项，写入新 `PORT`；用模板生成 `nginx\nginx.runtime.conf`；执行 `nginx -c ..\..\nginx\nginx.runtime.conf -t` 校验。
5. **启动后端**：注入环境变量，`Start-Process runtimes\node\node.exe index.js`，工作目录 `server\`，输出重定向到 `logs\server.out.log` / `logs\server.err.log`；轮询 `/api/health` 最多 30 秒。
6. **启动 nginx**：工作目录固定为 `runtimes\nginx`，用相对配置路径 `-c ..\..\nginx\nginx.runtime.conf`（避免 Windows 8.3 短路径导致 `CreateFile failed`）；等待端口可连接。随后在管理员权限下自动创建防火墙入站规则 `MindMap Web`（TCP 当前 Web 端口，`-Profile Any`）；非管理员时只打印手动命令，不中断部署。
7. **自检与输出**：执行 `check-deploy.js http://127.0.0.1:<WebPort>`（健康检查、入口页、JS 资源、WebSocket 四项）；写 `logs\deploy-state.json`；打印本机与局域网访问地址、配置/数据/上传/日志路径、停止与卸载命令、防火墙放行命令。

退出码：全部成功为 `0`；前置检查失败、端口占用、启动失败、自检有失败项时为 `1`。

`check-deploy.js` 手工用法：

```powershell
# 不带参数：读取 logs\deploy-state.json 的 webPort，读不到则默认 8080
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js
# 显式完整地址（改过端口时）
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js http://127.0.0.1:8080
# 只给端口号
C:\mindmap\runtimes\node\node.exe C:\mindmap\scripts\check-deploy.js 8080
```

不传参且默认值仍是 `http://127.0.0.1`（80 端口）、WebSocket 报 `ECONNREFUSED 127.0.0.1:80`，说明用的是旧版脚本或未带端口参数。实际端口可从 `logs\deploy-state.json` 的 `webPort` 读取。

幂等性：

- 重复执行会先停旧实例再启动，不会因“已存在配置/已存在目录”报错。
- `JWT_SECRET` 默认保留，不会因为重复部署导致用户被踢下线。
- `server\data`、`server\uploads` 不会被清空或覆盖。
- 端口被占用时是明确的失败，不会自动换端口。

### 8.2 启动 / 重启：`scripts\start.ps1`

```powershell
# 按 deploy-state.json / server.env / nginx.runtime.conf 解析端口
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\start.ps1

# 显式指定端口（必要时按模板重新生成 nginx.runtime.conf）
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\start.ps1 -WebPort 8081 -ApiPort 3001
```

- 只服务已部署环境：使用现有 `config\server.env`，**不会重新生成 `JWT_SECRET`**；文件缺失时直接报错并提示先执行 `deploy.ps1`。
- 端口优先级：命令行参数 > `logs\deploy-state.json` > `config\server.env` 的 `PORT` > `nginx\nginx.runtime.conf` > 默认 8080/3000。
- 端口与现有 nginx 配置不一致时，用 `nginx\nginx.template.conf` 重新生成；模板缺失时报错并建议改用 `deploy.ps1`。
- 启动前先停旧实例，所以**重复执行 `start.ps1` 就是重启**。
- 启动后端与 nginx 后执行 `check-deploy.js` 四项自检；管理员权限下确保 `MindMap Web` 防火墙规则存在。
- 退出码：`0` 成功；`1` 前置检查、端口占用、启动失败或自检失败。

场景对照：

| 需求 | 脚本 |
| --- | --- |
| 首次部署、改端口、改 `server.env` | `deploy.ps1` |
| 服务未运行，启动 | `start.ps1` |
| 已运行，重启 | `start.ps1`（内部先停后启） |
| 停止 | `stop.ps1` |
| 卸载（可选删数据） | `uninstall.ps1` |

### 8.3 停止：`scripts\stop.ps1`

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\stop.ps1
```

- 先按 `logs\nginx.pid` 结束 nginx（`taskkill /PID /T /F`，同时结束 worker），再清理本包路径下的残留 nginx 进程。
- 再按 `logs\server.pid` 结束后端；pid 文件丢失时，扫描可执行路径为本包 `runtimes\node\node.exe` 且命令行包含 `index.js` 的进程并结束。
- 删除 pid 文件；重复执行返回 0，不会报错。
- 加 `-Quiet` 可减少输出（供其他脚本调用）。

### 8.4 卸载：`scripts\uninstall.ps1`

```powershell
powershell -ExecutionPolicy Bypass -File C:\mindmap\scripts\uninstall.ps1
```

参数：

| 参数 | 说明 |
| --- | --- |
| `-RemoveData` | 同时删除 `server\data` 与 `server\uploads`；不加时保留数据 |
| `-Quiet` | 减少输出 |

行为：

- 先停止服务；删除 `logs\*.pid`、`logs\*.log`、`logs\deploy-state.json`、`nginx\nginx.runtime.conf`。
- 删除 `deploy.ps1` 创建的防火墙入站规则 `MindMap Web`（非管理员执行时只提示，不中断）。
- 默认**保留** `config\server.env`、`server\data\`、`server\uploads\`，方便重新部署后继续使用。
- 程序文件与 `runtimes\` 不删除；确认不再需要后，手动删除整个解压目录即可（不会留下注册表项或系统服务）。

### 8.5 开机自启

本包不注册 Windows 服务。可用「任务计划程序」：

1. 打开「任务计划程序」→「创建任务」。
2. 常规：勾选「不管用户是否登录都要运行」「使用最高权限运行」。
3. 触发器：新建「启动时」。
4. 操作：程序 `powershell.exe`，参数：
   `-ExecutionPolicy Bypass -File C:\mindmap\scripts\start.ps1`
   起始于 `C:\mindmap`。
5. 重启服务器后，浏览器访问 `http://<部署机IP>:8080/` 验证。

说明：开机执行 `start.ps1` 只复用现有 `config\server.env` 与 nginx 配置，不会重新生成 `JWT_SECRET`；需要改端口或配置时才用 `deploy.ps1`。

## 9. 升级与回滚

### 9.1 升级步骤（保留数据与上传目录）

1. 停止服务：`scripts\stop.ps1`。
2. 按 6.2 节备份 `config\server.env`、`server\data`、`server\uploads`。
3. 把新包解压到一个临时目录（例如 `C:\mindmap-new`）。
4. 把旧目录的 `config\server.env`、`server\data\`、`server\uploads\` 复制到新目录对应位置。
5. 停止旧目录后，把旧目录改名（例如 `C:\mindmap-old-20261108`），把新目录改名为 `C:\mindmap`。
6. 在新目录执行 `scripts\deploy.ps1`；自检全部通过、浏览器抽样验证后再删除旧目录。

也可以在原路径覆盖升级：先停服务与备份，再把新包内容覆盖到原目录（保留 `config\server.env`、`server\data`、`server\uploads`），最后执行 `deploy.ps1`。

如果只是脚本/nginx 模板修复（例如本次的 `start.ps1`、防火墙规则、`listen 0.0.0.0`），不必替换整包：只覆盖 `scripts\` 下对应脚本与 `nginx\nginx.template.conf`，再执行 `start.ps1` 或 `deploy.ps1` 即可，数据与 `server.env` 不受影响。具体命令见 [离线部署说明.md](离线部署说明.md) 8.1 节。

> 配置修复：旧版 `deploy.ps1` 生成的 `config\server.env` 存在换行错误（`JWT_SECRET=` 后换行，实际读到空值）。新版 `deploy.ps1` / `start.ps1` 读取时会识别该格式，自动合并为单行并回写，保留原密钥与 AI 配置；替换脚本后直接执行 `start.ps1` 即可修复并重启。仅当值为空时 `deploy.ps1` 才生成新密钥（旧 token 需重新登录）。

### 9.2 回滚

1. 停止服务。
2. 把新目录移开，把 `mindmap-old-<日期>` 改回 `mindmap`。
3. 如果升级后已经产生新数据，需要用升级前的 `app.db` 与 `uploads/` 备份恢复；否则直接使用旧目录中的数据。
4. 执行旧目录的 `scripts\deploy.ps1`（或旧版的启动脚本），完成自检。

### 9.3 数据库与版本兼容

`db.js` 使用 `CREATE TABLE IF NOT EXISTS` 建表，没有迁移框架。若未来版本新增表/字段，升级时通常可直接复用旧 `app.db`；但**降级前必须备份**，因为旧代码不识别新字段或新结构。任何结构变更都应以备份为前提。

### 9.4 前端更新

部署包内 `web/` 已构建完成，升级时直接替换 `web/` 即可，部署机不需要 Node 构建环境。若自行修改了前端源码，需要在有 `myweb/node_modules` 和 `../simple-mind-map` 的开发机上执行：

```bash
cd myweb
npm run build
```

再把 `myweb/dist/` 的内容覆盖到 `web/`。离线部署机没有 npm registry，无法在部署机安装前端依赖。

## 10. 安全与运维注意事项

- 必须保证 `JWT_SECRET` 唯一且足够随机；不要在多套部署间复用。`deploy.ps1` 生成的 48 字节 hex 已满足要求。
- `deploy.ps1` 在管理员权限下会自动放行 Web 端口（规则 `MindMap Web`，`-Profile Any`）。若需收紧到内网网段，可编辑该规则增加 `-RemoteAddress` 限制；不要放行 API 端口 3000：

```powershell
# 手工创建/更新的等价命令（改过端口时替换 8080）
New-NetFirewallRule -DisplayName "MindMap Web" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow -Profile Any
```

- 不要把 `server/data/app.db`、`config/server.env` 放入任何公开共享目录。
- 默认没有 HTTPS。若需要 HTTPS，可在 nginx 模板中增加 `listen 443 ssl` 与证书配置，并把前端同源规则保持不变（`window.location.protocol` 会自动选择 `wss://`）。
- 目标系统 Windows Server 2012 R2 与 Node.js 18 均已 EOL，不具备持续安全更新能力；这是本方案最大的长期风险。建议规划迁移到 Windows Server 2016/2019 及以上 + Node.js 20/22 LTS。

## 11. Linux 部署的限制与运行时准备

本包内只有 **Windows x64** 运行时，**不能**直接在 Linux 上运行 `runtimes\node\node.exe` 或 `runtimes\nginx\nginx.exe`，也没有提供 Linux 一键部署脚本。Linux 侧需要单独准备运行时，不能假装“一键可用”。

### 11.1 限制

- `scripts\deploy.ps1`、`start.ps1`、`stop.ps1`、`uninstall.ps1` 仅适用于 Windows PowerShell。
- Linux 需自行准备 `node` 与 nginx，并手工启动后端（包内不提供 Linux 启动脚本或 systemd 单元）。
- 部署包内没有 Linux 版的 Node/nginx 二进制；需要从联网机器下载后摆渡到内网。

### 11.2 在联网机器准备运行时

Node.js（推荐与本包一致的 v18.20.8；若目标 Linux 发行版支持，可改用 20/22 LTS）：

1. 下载：`https://nodejs.org/dist/v18.20.8/node-v18.20.8-linux-x64.tar.xz`
2. 校验：同目录的 `SHASUMS256.txt` 中找到 `node-v18.20.8-linux-x64.tar.xz` 对应行，执行 `sha256sum node-v18.20.8-linux-x64.tar.xz` 比对。
3. 摆渡到目标机后解压到例如 `/opt/node18`：
   `tar -xJf node-v18.20.8-linux-x64.tar.xz -C /opt`
   可把 `/opt/node-v18.20.8-linux-x64/bin` 加入 PATH，或在下文启动命令中直接使用该绝对路径。
4. 验证：`/opt/node-v18.20.8-linux-x64/bin/node -v` 输出 `v18.20.8`。

nginx（任选其一）：

- **推荐**：使用目标发行版 ISO/本地仓库中的 nginx 离线包（RPM/DEB），避免在目标机编译。
- 或从 `https://nginx.org/download/nginx-1.26.2.tar.gz` 下载源码，在联网机器准备好编译依赖（gcc、pcre、zlib、openssl），编译后把 `objs/nginx` 与 `conf/` 摆渡到目标机。
- 配置使用包内 `nginx\nginx.linux.conf`（默认监听 80、`root /opt/mindmap/web`、反代 `127.0.0.1:3000`），并按发行版调整 `user` 与路径。

### 11.3 Linux 部署步骤（概要）

```bash
sudo mkdir -p /opt/mindmap
sudo unzip mindmap-offline-win2012r2-20261108.zip -d /opt/mindmap   # 需系统有 unzip；否则先在别处解压再拷贝
sudo useradd -r -s /sbin/nologin mindmap || true
sudo chown -R mindmap:mindmap /opt/mindmap
# 编辑 /opt/mindmap/config/server.env，写入 JWT_SECRET，PORT 保持 3000
# 配置 nginx（见上），nginx -t 通过后启动
cd /opt/mindmap/server
set -a; . ../config/server.env; set +a
/opt/node-v18.20.8-linux-x64/bin/node index.js > ../logs/server.log 2>&1 &
/opt/node-v18.20.8-linux-x64/bin/node /opt/mindmap/scripts/check-deploy.js http://127.0.0.1
```

长期运行请使用发行版自带的服务管理（如自行编写 systemd 单元）；包内不再附带 Linux 启动脚本或单元文件。

## 12. 已知限制与未验证项

- **未在真实 Windows Server 2012 R2 上验证**：本开发机为 Windows 11 x64，完成了包内 Node 18.20.8 启动、后端健康检查、注册、sql.js 建库、nginx 端到端与 WebSocket 自检；Server 2012 R2 上的实际启动仍需在目标机执行一遍 `deploy.ps1` 确认。
- **Node 18 已 EOL**：2025-04-30 之后不再有安全更新；且按官方口径，Server 2012 R2 已不在 Node.js 支持范围。详见 1.2 节。
- **nginx Windows 版为 beta**：只有单个 worker 实际工作，高并发能力有限；官方未声明 Server 2012 R2 为受测平台。
- **无 HTTPS、无内置服务注册、无日志轮转**：需要按第 8、10 节自行配置。
- **客户端**：Windows 10 / 11 + 当前版本 Chrome / Edge；服务端不运行浏览器。详见 1.6 节。
- **AI 功能依赖外部可达的 OpenAI 兼容服务**：完全隔离的内网不可用。
